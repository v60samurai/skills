IMANI'S WRITE-UP: TIDELINE V1 IMPLEMENTATION RECOMMENDATION

Status: my recommendation. Not approved.

A. Recommended architecture

A1. Repository interface. All data access goes through one interface so the UI never knows where numbers come from.

```ts
interface InsightsRepository {
  getOverview(scope: PartnerScope): Promise<OverviewData>
  getListings(scope: PartnerScope, query: ListingQuery): Promise<Page<ListingRow>>
  getListingDetail(scope: PartnerScope, listingId: string): Promise<ListingDetail>
  getBenchmark(scope: PartnerScope): Promise<BenchmarkData>
}
```

A2. Fixture adapter. `FixtureRepository` implements the interface by reading `fixtures/partners/<partnerId>.json`. At least three fixture partners: one healthy, one declining, one with a peer set under 5 so the suppression state is exercised.

A3. API adapter. `ApiRepository` implements the same interface and throws `NotImplemented` for now. It exists so the swap to real data is one line in the composition root.

A4. Shared scope object. One `PartnerScope` drives every tab:

```ts
type PartnerScope = {
  partnerId: string
  dateRange: { from: string; to: string }   // ISO dates, inclusive
  compareTo: 'previous_period' | 'same_period_last_year'
  market: string | null
}
```

Scope lives in the URL, so a link reproduces the exact view.

A5. Routes. `/partners/:partnerId/overview`, `/partners/:partnerId/listings`, `/partners/:partnerId/benchmark`. Date range and comparison go in query params (`from`, `to`, `compare`). `/partners/:partnerId` redirects to overview.

A6. Metric provenance. Every metric value carries `{ metricId, sourceView, refreshedAt }`. A tooltip on each tile and column header shows them. This is also what Ask Tideline would cite later.

A7. View states. Every data region handles four states: loading (skeleton, not a spinner), empty ("No bookings in this range"), error (message plus Retry, other regions stay usable), partial (some metrics missing: show the ones present and mark the missing tile "Unavailable").

A8. Testing. Unit tests for delta math (percent, percentage points, zero baseline). Component tests for Listings sort, search and pagination. One integration test per tab against `FixtureRepository`. A manual checklist run before each review.

A9. No global state library. URL plus React Query cache is enough for three tabs.

B. Roadmap

Phase 0: Prototype cleanup. Remove the hardcoded Blue Heron Ferries data, the onboarding carousel and the AI Insight card. Exit: the prototype renders from a fixture file.

Phase 1: Shell and Overview. Header with partner switcher, date range and comparison toggle, tab bar, then the four tiles and trend chart. Depends on Phase 0.

Phase 2: Listings. Table, search, sort, pagination, row drawer. Depends on the shell from Phase 1.

Phase 3: Benchmark. Percentile bars and the fewer-than-5 suppression state. Blocked on the peer set definition for final copy, buildable against fixtures before that.

Phase 4: Joint review. Imani, Dario and Kofi walk all three tabs on fixtures. Dario signs off layouts. Output is a punch list.

Phase 5: Leadership review. Kofi demos to the head of partnerships. Go or no-go for real data work.

Phase 6: Real data planning. Renata finalizes `partner_daily_v2` and `listing_daily_v2`, the metric contract is signed off, DATA-4471 is closed, and `ApiRepository` is designed. No UI work.

Phase 7: Additional deterministic tabs. Reviews and Complaints, after the reviews data owner is known. Still no AI.

Phase 8: Ask Tideline discovery. Collect real questions from 20 account manager interviews into a question log, and classify which ones the metrics can answer.

Phase 9: Ask Tideline MVP. Text only, read only, every answer cites metric ids from the provenance model. No actions.

Phase 10: Voice. Speech in and out on top of the Phase 9 answers. Depends on Phase 9 answer quality passing its evaluation set.

Phase 11: Task execution. Tideline drafts a partner follow-up email. A human approves before send, always.

Phase 12: Delegated agents. Tideline hands longer tasks to other agents and reports back. Needs an observability and audit story first.

Phases 0 to 5 are the V1 prototype track. Phase 6 and 7 follow a go decision. Phases 8 to 12 are future direction and are not scoped.
